# TestHistory UI Design System

## Цель

Интерфейс TestHistory должен ощущаться как рабочий инструмент для QA/DevOps: плотный, читаемый, предсказуемый, с цветами, которые помогают различать состояние данных, а не украшают экран ради украшения.

## Палитра

Основная палитра:

| Роль             | Цвет             | HEX       | Где использовать                                              |
| ---------------- | ---------------- | --------- | ------------------------------------------------------------- |
| Основной акцент  | Синий            | `#2563EB` | Primary buttons, active tabs, focus ring, selected navigation |
| Сильный акцент   | Синий насыщенный | `#1D4ED8` | Hover/pressed primary actions, important links                |
| Мягкий акцент    | Голубой фон      | `#E8F1FF` | Active filters, selected rows, soft callouts                  |
| Вторичный акцент | Cyan             | `#0891B2` | Integration/link features, informational highlights           |
| Успех            | Зеленый          | `#159947` | Passed, enabled toggles, active healthy states                |
| Предупреждение   | Amber            | `#D97706` | Broken, partial data, warning banners                         |
| Ошибка           | Red              | `#DC2626` | Failed, destructive actions, denied states                    |
| Текст            | Ink              | `#172033` | Primary headings and body text                                |
| Вторичный текст  | Muted            | `#526172` | Helper text, metadata, timestamps                             |
| Линии            | Border           | `#D7E1EE` | Dividers, table rows, panel borders                           |
| Фон страницы     | Cool surface     | `#F3F7FB` | App/page background                                           |
| Фон карточек     | White            | `#FFFFFF` | Panels, dialogs, list rows                                    |

Не делать интерфейс монохромным. Серый допустим только как нейтральная подложка, но важные состояния должны иметь цветовой смысл.

## Правила Цвета

- Primary action всегда синий `#2563EB`; destructive action красный `#DC2626`.
- Enabled switch использует зеленый градиент `#159947 -> #0F766E`; disabled switch серо-голубой `#D7E1EE`.
- Интеграции, ссылки и внешние системы получают cyan/blue акценты, чтобы отличаться от обычных настроек.
- Warning/partial состояния не должны быть красными: использовать amber.
- Empty/disabled состояния: заголовок серый, тело блока не показывать, если данных нет.
- Focus-visible обязателен: синий outline или box-shadow, не только изменение фона.

## Типографика

- Не использовать отрицательный letter-spacing.
- Заголовки блоков компактные: 14-16px, 800 weight, высота шапки одинаковая в рамках одного экрана.
- Текст внутри кнопок и баблов не должен обрезаться и вылезать. У кнопок должны быть `min-width: 0`, `overflow: hidden`, `text-overflow: ellipsis`.
- Баблы/бейджи: минимум 12px, 700-800 weight, контрастный текст. Слишком мелкие серые баблы запрещены.

## Компоненты

### Диалоги

- Header должен быть визуально отделен от body: мягкий blue/cyan фон или clear border.
- Body должен иметь чистый белый/почти белый фон, helper text muted, поля с заметным focus.
- Footer фиксируется визуально: светлая подложка, primary справа.
- Toggle/switch в диалоге занимает всю строку, не должен сжиматься до иконки или трека.

### Таблицы и списки

- Настройки, интеграции, токены, участники, дефекты и история показываются списками/таблицами, а не набором больших карточек.
- Большие списки всегда с пагинацией: дефолт 10, варианты 10/20/50.
- Заголовки колонок должны быть темнее обычного muted text и иметь достаточный контраст.
- Редактирование строк только через явную кнопку-карандаш. Добавление новой сущности не должно менять список до сохранения.

### Сайдбар и пользователь

- Карточка пользователя: аватар + имя + роль. Не дублировать `name/email/role`, если значения совпадают.
- Роль показывать человекочитаемо: `Администратор`, `Пользователь`, `Владелец`, etc.
- Logout вторичен, но всегда видим и не должен растягивать карточку.

### Project Settings

- `Доступ`: участники списком; матрица прав только по кнопке информации.
- `API токены`: создание, копирование нового токена, отзыв токена в одной таблице.
- `Интеграции`: таблица строк; включение через switch; создание/редактирование только через диалог.
- `Хранение`: таблица сроков полностью редактируемая, а не read-only summary.

## Чеклист Перед Сдачей UI

- Все вложенные уровни имеют отдельный URL/hash и переживают refresh.
- Нет видимого английского текста, кроме логинов, названий проектов, технических label values и внешних ключей вроде `JIRA_ISSUE`.
- Нет кнопок с вылезающими иконками/текстом.
- Нет карточек внутри карточек без необходимости.
- Empty блоки не занимают большое пустое тело.
- Все интерактивные элементы имеют hover/focus/disabled состояния.
- Переключатели, чекбоксы и кнопки проверены визуально в диалогах и таблицах.
- `npm run guard:module-size`, web build и web tests проходят.
